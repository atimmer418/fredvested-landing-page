# Go-live checklist

One ordered list from the state of `develop` on 2026-09-26 to the landing page being public. Work it top to bottom. Each step says who does it (Andrew, counsel, or a code change), what it depends on, and how to verify it. Details live in the six documents this is pulled from (`analytics-events.md`, `utm-conventions.md`, `analytics-dashboard-setup.md`, `email-funnel.md`, `resend-setup.md`, `analytics-qa.md`) and the completion review (`analytics-implementation-review.md`); the intent is that you do not need to open them to get through this list.

Legend for "Who": **Andrew** (dashboards, DNS, variables, merges), **Counsel** (copy and policy), **Code** (a change in the repo, with tests, by whoever is doing the code).

## A. Before anything else: the code is done

## E. Railway production (API)

16. **Production variables.** Who: Andrew. Depends on: steps 5, 11, 12, 13. Set on the prod service: `MYSQLHOST`, `MYSQLPORT`, `MYSQLDATABASE`, `MYSQLUSER`, `MYSQLPASSWORD` (already there), `CLOUDFLARE_TURNSTILE_SECRET` (the real key's secret), `CORS_ALLOWED_ORIGINS=https://fredvested.com,https://www.fredvested.com`, `RESEND_API_KEY` (prod key), `RESEND_WEBHOOK_SECRET` (prod endpoint), `POSTAL_ADDRESS` (required, no default), `API_PUBLIC_URL=https://lpapi.fredvested.com` (https, never http; also the prod default, so unset gives the same), `EMAIL_FROM` (default `FRED <fred@fredvested.com>`), `WAITLIST_DOUBLE_OPT_IN=true` (also the default), and `WAITLIST_US_ONLY` (defaults to `true` in prod: set it to `false` only if you want to drop the geo gate). Leave `LANDING_URL` unset: the prod profile has no placeholder for it and `LandingUrls` defaults to `https://fredvested.com`. `EMAIL_REPLY_TO` is optional (default `help@fredvested.com`). The base file's `LOG_LEVEL`, `SPRING_WEB_LOG_LEVEL`, `JPA_SHOW_SQL`, `JPA_DDL_AUTO` and `PORT` placeholders are overridden by fixed values in the prod profile, so they do nothing there; never set `JPA_DDL_AUTO` anywhere. No variable may be created empty: the app treats a blank as unset and logs a WARN naming it, but a required one still fails startup. Verify: every value reads back correctly in the Variables tab; none is blank.

17. **Backup, snapshot and Flyway dry-run against prod's schema.** Who: Andrew. Depends on: step 16 (the variables), and nothing has been deployed to prod yet. This is the rule in CLAUDE.md "Schema Migrations": prod is still on the pre-Flyway 6-column table, and V1 will baseline it, then V2 to V5 will run. Do: Railway -> prod MySQL service -> Backups: take a backup. Then Variables: copy the public connection values. Then on your machine: `mysqldump -h HOST -P PORT -u USER -p --no-data DATABASE > snapshot-schema.sql` (no `flyway_schema_history` dump: prod has never run Flyway, so the table does not exist yet); `mysql -u root -p -e "DROP DATABASE IF EXISTS fred_snapshot; CREATE DATABASE fred_snapshot"`; `mysql -u root -p fred_snapshot < snapshot-schema.sql`; then from `backend/`: `./gradlew bootRun --args='--spring.profiles.active=local --spring.datasource.url=jdbc:mysql://localhost:3306/fred_snapshot?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC'`. Verify: the log shows `Successfully baselined schema with version: 1`, then `Migrating schema ... to version "2 - add calculator input columns"` through `"5 - confirmed source and legacy backfill"`, then `Started WaitlistApplication`. The snapshot is schema only (no rows), so the legacy backfill can only be checked on prod itself after step 18. Any `APPLICATION FAILED TO START` or `Schema-validation` line means stop and fix the migration, never the setting. Drop `fred_snapshot` afterwards.

18. **Deploy prod and read the log.** Who: Andrew. Depends on: step 17 passed, and section F's merge if prod deploys from `main` (check the Railway service's branch; if it deploys from `develop`, this happens on push). Verify: the same Flyway lines as the dry-run, then `Started WaitlistApplication`; no `BlankEnvironmentVariables` WARN (every variable was set on purpose); `curl -I https://lpapi.fredvested.com/api/waitlist/confirm?token=x` is 200 (the HEAD no-op); `curl https://lpapi.fredvested.com/api/waitlist/stats` returns aggregates only, with `count` equal to the number of legacy rows; on prod's database, `SELECT confirmed_source, COUNT(*) FROM waitlist_signups GROUP BY 1` shows every pre-launch row as `legacy` (with `confirmed_at = created_at`) and nothing else; an OPTIONS preflight from `https://fredvested.com` is 200 and from a random origin is 403.

## H. The first 24 hours

Verify each of these once a few hours in: Plausible Realtime and the goals (pageviews and the eight events arriving, no `Waitlist Failed` spike; the Business plan's usage counter, remembering pageviews and custom events are billed, engagement is not); Resend (delivered rate, any bounce or complaint; every webhook delivery 200); Railway prod logs (no `ERROR`, no `Send attempt ... failed`, no `Giving up on message`, no `Invalid CORS request`, no `BlankEnvironmentVariables` WARN); the database: `SELECT * FROM v_waitlist_funnel` (submitted, confirmation_sent, delivered, confirmed by source, rates) and `SELECT * FROM v_email_suppressions` (anyone suppressed, and why).

23. **Known gaps to keep in mind on day one.** Who: Andrew, awareness only. A token cannot be re-minted after an ambiguous send (the person uses "resend the email"). A mail sandbox that executes JavaScript confirms the row itself. Confirmations that overlap at exactly 300 founders could exceed the cap by a few (the count and the write are not serialised across transactions). Re-submitting an unconfirmed address is answered like a fresh signup and re-sends the confirmation (address-limited to 1 per 10 minutes, 3 per day). Timestamps in the database are Eastern wall-clock; do not mix `NOW()` edits with them.

24. **Later, not launch blockers.** DMARC to `quarantine` after two to four weeks of clean reports (step 10). Tag every social bio link and campaign per `utm-conventions.md` before posting. The founder-cap and stats semantics count confirmed rows only; the about-page numbers appear at 25 or more. If daily volume ever approaches 5,000, add the `List-Unsubscribe` headers back per template (the POST endpoint already honours them). The referral share prompt marked `TODO` on `confirmed.html`.
